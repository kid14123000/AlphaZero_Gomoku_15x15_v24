## v18 — ch2 视角颜色通道修复（2026-08-22 设计，v12 服务器原样+只改 ch2）

### 根因链（Rapfi 棋力测评暴露，完整证据链）

**触发**：本地 web `/eval` 页接入 Rapfi（世界级五子棋引擎）做绝对棋力锚点——v12 权重 vs Rapfi 最弱档仍"三岁小孩"（棋谱名即诊断：`黑棋无视白棋`/`看不见活三`/`活上不堵`）。

**复盘定位**（`scripts/replay_rapfi_ignore.py`，局面 = Rapfi 棋谱第 8 手后白活三 (7,5)(6,6)(5,7)，轮到黑）：

| 环节 | 结果 | 结论 |
|---|---|---|
| policy 先验 | 堵点 (4,8)=2.92% 排名#1、(8,4)=1.68% 排名#2；实际走 (2,8) 排名#109 | **policy 完全知道该堵** ✅ |
| 根局面 value | 黑视角 +0.726 | 乐观（白活三判黑大优）|
| **MCTS 后继 Q** | 不堵 (2,3) q=+0.618 / 堵 (4,8) q=-0.815 | **value 奖励放任、惩罚防守** 💀 |
| **防守评估方向探针**（用户设计） | 随意丢白视角 value(-0.277) < 堵上白视角 value(-0.057)，it188/193/196 三代颠倒 | value 认为"放任威胁对白更不利"= 颠倒 |
| 视角反对称性 | 黑视角 v + 白视角 v = -0.65~-0.71（应≈0）| **视角语义破坏** |
| ch2 扰动实验 | ch2=1→0，value -0.976→+1.000 饱和 | **网络把 ch2 当"执黑"信号** |
| 训练数据 player 分布 | 黑 50.7% / 白 49.3% 均衡 | 排除数据偏置 |

**根因**：**v8 引入 4ch 输入时，ch2（当前玩家颜色通道）被写成恒 `1.0`**——网络 196 代训练从未见过 ch2=0（白视角）的输入，学到"我永远执黑"。canonical 视角化（board×player）丢掉了"当前玩家是黑还是白"的信息（黑先手是实质信息），ch2 本应补回却没给 → 白视角局面评估系统性错乱 → **防守（堵白棋威胁）被 value 负评 → MCTS 不防守 → "三岁小孩"**。08-19 已发现"反对称 v_b+v_w≠0"但未追到"ch2 恒 1 是根因"这一层。

**三处独立验证同指一因**：Rapfi 实战（无视活三）⇔ 防守评估方向探针（颠倒）⇔ 败局库测试 MSE 2.5-3.2（崩）。

### 复盘：v8 当年为什么"信誓旦旦说改好了"（2026-08-22 用户质询）

v8 建立时（2026-08-07）声称"颜色翻转 = 交换 ch0/ch1 → 颜色对称性结构性满足"，并引用**代4 定向互补 0.0021 vs v6 it99=1.82** 当证据。复盘后确认：**这句话只对了一半，且验证标准选错了**。

1. **"颜色对称"和"视角健康"被混为一谈**：
   - 治好的：ch0/ch1 交换对称（相对视角：己方/对手）——v2/v6 的"重黑轻白"（同局面黑白视角评估不对称）确实结构性解决了
   - 没解决的：**绝对颜色（黑先手）信息**——canonical 视角化（board×player）把"当前玩家是黑是白"抹掉了，ch2 本应补回却写死 1.0。这是另一个维度，当时完全没意识到
2. **验证标准选错**：用"定向互补 0.0021"这个漂亮数字当证据，但那是**构造的定向测试**；同一时期"随机 200 局面互补 0.51（≈随机）"的红灯被选择性忽略。**教训：验证必须用真实分布 + 反对称硬指标（v_b+v_w≈0），定向探针只能当辅助**
3. **08-19 二次放过**：反对称 v_b+v_w≠0 探针已建，定位"ch2 视角平面被忽略"，但把结论停在"网络没学会"，没追问"通道设计本身是否给错"。**教训：探针红了要追到输入表示层，别只怪网络**

### 为什么必须从零训练（不能接着 v12 权重）

用户原计划"接着 v12 权重续训 v18"，对照实验证明**会炸**（`scripts/compare_ch2_blast.py`，局面=白活三）：

| 网络 | 黑视角(ch2=1) | 白视角(ch2=0) | 判定 |
|---|---|---|---|
| v12 权重（接着练方案）| -0.076 | **+1.000 饱和** | 💀 OOD 炸 |
| 随机初始化（v18 从零）| -0.004 | -0.004 | ✅ 无偏 |

机制：v12 训了 196 代**只见过 ch2=1**（"我永远执黑"），白视角 ch2=0 对它 = 从未见过的输入 → value 饱和；且 BN running stats 全在 ch2 恒 1 分布下累计，继承即全通道失配。**从零训练**让 ch2 从第一代起就平等参与学习（随机网络对 ch2=0/1 无偏），无旧包袱、不会炸。

### v18 方案

**原则（用户拍板）**：按 v12 服务器原样复制（`Gomoku-v0_pt_v12.py` md5 4bff0ad3... 与本地 git 一致），**只改 ch2**，其他适配调用链。

**改动**：
| 位置 | 改动 |
|---|---|
| `make_input` | 加 `player` 参数 → `out[2] = 1.0 if (player is None or player==1) else 0.0` |
| `_to_planes` | 加 `players` 参数，None 默认黑（诊断探针兼容）|
| `predict_inference` / `predict` | 加 `players` 参数，None 默认黑 |
| `learn()` | `inp[:, 2] = (players == 1)[:, None, None]`（训练数据已有 players）|
| `search()` | 加 `player` 参数，递归传 `next_player` |
| `decide()` | `search(..., player=player)` |
| worker | `Gomoku-worker_v18.py`（import 指向 v18）|

**ch2 语义（用户定义）**：当前玩家执黑 = 全 `1`，执白 = 全 `0`。

**验证**（`scripts/verify_v18_ch2.py`）：ch2 编码正确 ✅ / 自对弈不崩 ✅ / **顺带实锤根因**——v12 权重在 ch2=0 输入下输出饱和 +1.000（从没见过白视角输入，OOD 瞎输出）。

**注意**：v12 权重不可原地修复（已训 196 代）；v18 必须从零/从 v12 重训才能让网络学会 ch2 语义。

### 验收标准（2026-08-22 用户拍板：不许再用"好看的指标"糊弄）

| 层 | 指标 | 通过线 | 失败含义 |
|---|---|---|---|
| **结构**（代0 前）| `make_input` ch2 编码 | 黑=1/白=0，自对弈不崩 | 改动未生效 |
| **视角健康**（核心，每代）| 反对称探针 v_b+v_w（同局面黑白视角 value 之和）| ≈0（\|和\|<0.15）| ch2 语义没学会 → 返工 |
| **实战防守**（代 N）| 防守评估方向探针（堵上 vs 放任，对方视角）| 放任 > 堵上 | value 仍颠倒 → 没修好 |
| **棋力**（判定点）| PK vs v12 同期权重 | 见 PK 规矩 | 相对进步 |

**核心纪律**：视角对称性用**真实分布随机局面**的 v_b+v_w 衡量，不用定向构造探针；探针红了必须追到输入表示层。

### 关键修复2：MCTS 递归 ch2 传递 bug（2026-08-22 傍晚，用户追问"视角反转时通道传输"发现）

**根因**：`boardgame2.get_next_state` 返回 `next_player = -player`，而 search 调用 `next_step((board, BLACK))` 恒传 BLACK=1 → **next_player 恒 = -1**（是"视角翻转标记"不是"绝对颜色"）。v18 递归误传 `player=next_player` → 从第 2 层起 ch2 恒=0（白），黑视角层被网络当成白视角，**MCTS 深层 value/policy 评估全错**。

**影响链**：decide 根节点 ✅ → 第1层碰巧对（-1=白）→ 第2层起全错（黑视角层 ch2=0）→ 自对弈数据（代0/代1）在错误视角评估下产出 → 训练数据带病。

**修复**：递归传 `player=-player`（绝对颜色每层翻转）+ predict 侧 player=None 兜底默认黑。验证：递归链 1→-1→1→-1 ✅、自对弈 27 步无异常 ✅。

**⚠️ 决策**：代0/代1 数据在 bug 下产生 → 需重置从零重训（见下文）。

### 🔬 BN train/eval 不一致复现（2026-08-22 深夜，policy 头 eval 全死）

v14 的 BN 不一致在 v18 重演且更极端——**eval 模式 policy 头 ReLU 全死（激活率 0%），train 模式正常（62-68%）**：

| 口径 | policy_relu 激活率 | 黑活三 top1 | 熵 |
|---|---|---|---|
| train 模式 | 62-68% | 5.88% | — |
| eval 模式（it4/5）| 0% | 0.44%（均匀）| 5.416（完全均匀）|

**机制**：policy_bn 的 running stats（EMA）滞后于当前权重分布——实测 it5 `running mean=-6.31 vs 当前 batch mean=-13.98`，**滞后 +7.67**；归一化后 z(running)=-1.14（全负 → ReLU 死）vs z(batch)=+0.15（激活 51.3%）。v12 同期对照：it0-3 也全死 → it4 自愈（10.7%）——"死着起步→复活"先例。v18 特殊性：**先活后死**（it0 活 86% → it4 死）= 振荡，比 v12（从未活过）更可能再活。

**momentum 方向验证**：用户问"之前调大到 0.3 失败是不是调反了"——**没调反**（momentum 大=更新快=滞后小）。滞后量 +7.67 巨大，momentum 0.1→0.3（更新快 3 倍）能显著减滞后、救 eval——但只治标（残余不一致还在）+ 早期震荡风险。**v12 先例证明自愈可行（v12 没调也复活了），用户拍板继续观察不干预**。

**复活期间靠 value 撑着**：policy 均匀时 PUCT 探索项（c·P·√N）对每点相同 → 选择由 q 项（value）主导 → 棋谱质量随 value 提升 → 良性循环（好棋谱 → value 更好 → 棋谱更好）。v2 实证同构：value 先起（it16）→ policy 追上（it32-60）→ 平衡（it45-150）。

### 🌡️ 温度调度修正（2026-08-23 凌晨，用户拍板，重大训练质量事件）

**用户发现的问题**：15x15 五子棋推荐前 16 手 `tau=1.0`、之后 `tau=1e-3`（接近贪心），而我们"基本全局 1，太夸张了"。

**根因（代码级实锤）**：旧调度 `total_est = max_moves // 2 = 225//2 = 112`，按满盘估计对局长度；但**实际对局只有 ~45 手**（均步 43-49）→ 终局段（`step >= 102`）永远走不到 → 中段线性插值在 step=45 时 frac=(45-15)/87=0.34 → `temp≈0.74` → **实际整局 temp 都在 0.74-1.0，几乎全程随机采样**。棋谱质量低、policy 学得慢（威胁识别靠后、空盘均匀均与此相关）→ 这解释了 v18 早期很多"慢热"现象。

**修改**（`Gomoku-v0_pt_v18.py`，三处）：
1. `TEMP_HIGH_MOVES = 15 → 16`（前16手）
2. 调度逻辑：`step < 16 → temp=1.0`；否则 `temp=1e-3`（删掉 112 估计 + 线性插值 + 0.05 终局段）

**🚨 NaN 崩溃事故（02:07 重启即崩，当场抓出）**：temp=1e-3 时 `soft = np.exp(log_p/temperature) = exp(log_p×1000)`，policy 是 log 概率（约 -5.4~-20）×1000 = -5400~-20000 → **exp 全部下溢为 0** → `soft.sum()=0` → `0/0=NaN` → `ValueError: probabilities contain NaN` → 主进程恢复 self_play 即崩。旧调度 temp 最小 0.05（exp(-5.4/0.05)=exp(-108)≈0 但不全消失）所以从未触发。**修复：`temperature <= 1e-2` 直接 argmax**——1e-3 本义就是"接近贪心"，argmax 等价且数值安全。**教训：改 temp 下限到 <1e-2 必须同步检查 exp 路径下溢**。

**验证**：调度模拟（step 0-15→1.0 / 16+→1e-3）✅ / decide 数值（1e-3 走 argmax 无 NaN）✅ / 重启后主进程+9工兵全活、02:12 后 0 Traceback ✅ / 三地一致（本地/服务器 md5 `9fbeab02`）✅ / git `2f7feea` ✅。
